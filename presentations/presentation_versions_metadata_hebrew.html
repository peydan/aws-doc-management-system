מטא-דאטה מתקדם: פיצ'ר Amazon S3 Object Annotations

פתרון מהפכני לאחסון מטא-דאטה עסקי עשיר ללא מגבלות ה-2KB וללא שכפול קבצים בינאריים

S3 Object Annotations Feature
❌ המגבלות בשיטות המסורתיות ב-S3
  • ✕
    S3 User Metadata Headers (x-amz-meta-*): מוגבל ל-2 KB סך הכל לכל הכותרות. אינו מאפשר מבנה JSON עשיר, היררכיות או ולידציה מורכבת.
  • ✕
    חוסר אפשרות לעדכון ישיר (Strict Immutability): שינוי כותרת מטא-דאטה דורש ביצוע CopyObject מלא – פעולה שמשכפלת את כל הבייטים הבינאריים ויוצרת גרסת קובץ S3 חדשה ומיותרת!
  • ✕
    Sidecar Files (.metadata.json): יוצר ריבוי קבצים, חוסר סנכרון במחיקות/גרסאות ועלויות כפולות של קריאות S3 API.
✨ היתרונות של Amazon S3 Object Annotations
Native AWS SDK API
  • ✓
    נפח של עד 1 MB לכל Annotation: מאפשר אחסון מבני מטא-דאטה עשירים, רשימות חתימות, שדות עסקיים מורכבים והיסטוריית עריכות.
  • ✓
    עדכון ישיר (In-Place Mutation): פקודת PutObjectAnnotationCommand מעדכנת את המטא-דאטה ישירות על גרסת ה-S3 הקיימת, ללא יצירת גרסה בינארית כפולה וללא שכפול בייטים!
  • ✓
    צימוד מוחלט לגרסת האובייקט (Bound to VersionId): לכל גרסת תוכן בינארי יש אנוטציה ייעודית בשם document-metadata הצמודה ל-s3_version_id שלה.
  • ✓
    מוכנות ל-S3 Metadata Apache Iceberg & Athena: האנוטציות זורמות באופן טבעי לטבלאות אנליטיקה ו-SQL בארגון.

מבנה המטא-דאטה ומטריצת מוטביליות (Mutability)

הפרדה קשיחה בין שדות מערכת מוגנים (System Envelope) לבין שדות עסקיים הניתנים לשינוי

Data Governance & Immutability
🏛️ מעטפת מערכתית (Base System Envelope)
Immutable / Monotonic

שדות תשתיתיים המשותפים לכל מחלקות המסמכים בארגון. נחסמים לשינוי ישיר ע״י לקוחות:

  • document_id – מזהה ייחודי קבוע (UUID v4). קבוע לנצח
  • document_class – סיווג המסמך (למשל loan_agreement). קבוע
  • application_version – מספר גרסת הקובץ הבינארי. קבוע לגרסה
  • metadata_revision – מונה גרסת מטא-דאטה אופטימי. מנוהל מערכתית
  • content_length & content_checksum – גודל ו-SHA256 של הקובץ. מחושב בינארית
  • created_at / created_by – נתוני יצירה וביקורת. בלתי מחיק
💼 שדות עסקיים (Business Attributes)
Mutable via PATCH

שדות ספציפיים למחלקת המסמך המוגדרים בתבנית הסכמה וניתנים לעריכה ב-PATCH:

  • customer_id – מזהה לקוח / ת.ז / ח.פ. ניתן לעריכה
  • loan_number – מספר הלוואה או חוזה. ניתן לעריכה
  • loan_amount_minor_units – סכום ההלוואה באגורות/סנטים. ניתן לעריכה
  • currency – מטבע (ISO-4217, למשל ILS, USD). ניתן לעריכה
  • loan_type – סוג הלוואה מתוך Enum (למשל MORTGAGE). ניתן לעריכה
  • signed_date – תאריך חתימה (ISO 8601 Date). ניתן לעריכה
שם השדה במטא-דאטה סיווג כלל שינוי (Mutability Rule) מנגנון עדכון והגנה
document_id, document_class זהות מסמך Strictly Immutable נקבע פעם אחת ביצירה. ניסיון עריכה ב-PATCH נדחה ב-400 Bad Request.
application_version, content_checksum נתוני תוכן Immutable per Version משתנה רק בעת העלאת קובץ בינארי חדש (POST /versions).
metadata_revision בקרת מקביליות System Monotonic (N → N+1) מקודם אוטומטית ע״י המערכת בכל עדכון מטא-דאטה תחת נעילה אופטימית.
branch_code, customer_id, loan_type נתונים עסקיים Mutable Business Data מתעדכן ב-PATCH /v1/documents/{id}/metadata בכפוף ל-JSON Schema.

מודל הגרסאות הדו-ערוצי (Dual-Track Versioning)

הפרדה מוחלטת בין גרסת תוכן בינארי (Content Version) לבין רוויזיית מטא-דאטה (Metadata Revision)

Dual-Track Versioning
📄 ערוץ 1: גרסת תוכן בינארי (Content Version)
POST /documents/{id}/versions

מופעל כאשר מועלה קובץ PDF/תמונה פיזי חדש למסמך קיים (למשל מסמך חתום מחדש או נספח מתוקן):

  • ← נוצרת גרסת S3 חדשה: מקבל s3_version_id ייחודי.
  • ← קידום גרסה: application_version מקודם ($V \to V+1$).
  • ← איפוס רוויזיה: metadata_revision מתאפס ל-1 עבור הגרסה החדשה.
  • ← חישוב מחדש: content_length ו-content_checksum (SHA256) מחושבים מחדש.
  • ← רשומת היסטוריה ב-DynamoDB: נשמרת רשומה ייעודית VER#000000000V לשליפה בעתיד.
✏️ ערוץ 2: רוויזיית מטא-דאטה (Metadata Revision)
PATCH /documents/{id}/metadata

מופעל כאשר מעדכנים שדות עסקיים (למשל תיקון סכום, שינוי סטטוס, עדכון סניף) ללא שינוי בקובץ הפיזי:

  • ← ללא גרסת S3 חדשה: הקובץ הבינארי וה-application_version אינם משתנים!
  • ← קידום מונוטוני: metadata_revision מקודם ($N \to N+1$).
  • ← עדכון ישיר באנוטציה: PutObjectAnnotation מעדכן את ה-JSON הצמוד ל-S3 VersionId הקיים.
  • ← נעילה אופטימית (OCC): חובה לשלוח expected_metadata_revision. התנגשות תחזיר 409 METADATA_CONFLICT.
  • ← עלות ואחסון מינימליים: אפס שכפול בייטים בינאריים, מהירות ביצוע של פחות מ-800ms.
🛡️ מנגנון הנעילה האופטימית (Optimistic Concurrency Control - OCC)
1. בדיקת רוויזיה נוכחית:

הלקוח שולח expected_metadata_revision: 2 בבקשת ה-PATCH.

2. התניה אטומית ב-DynamoDB:

פקודת UpdateItem מוודאת בטרנזקציה ש-current_metadata_revision = 2.

3. טיפול בהתנגשות (409 Conflict):

אם תהליך אחר כבר שינה את הרוויזיה ל-3, הבקשה נחסמת מיד ללא דריסת נתונים (Lost Update Prevention).

Developer & Architecture Guide

1. יצירת קובץ schemas/bank_statement-v1.json

הסכמה מגדירה את מעטפת המערכת החובה, שדות עסקיים ספציפיים למחלקה, טיפוסים מדויקים (מחרוזות, מספרים, תאריכים, Enums), ואוכפת additionalProperties: false למניעת שדות זרים.

4. שלב 2 (העתידי): Dynamic Schema Registry via REST API

בשלב הבא (Phase 2), מנהלי מערכת יוכלו לרשום סכמות חדשות בזמן ריצה ללא צורך ב-CDK Deployment או שינוי קוד, באמצעות קריאת REST API מאובטחת:

// 1. רישום סכמה חדשה במצב DRAFT POST /v1/admin/schemas Authorization: Bearer <JWT-Token> Content-Type: application/json { "document_class": "bank_statement", "version": 1, "schema_definition": { ... } } // 2. הפעלת הסכמה בייצור (משדר אירוע EventBridge שמרענן מטמון) POST /v1/admin/schemas/bank_statement/versions/1/activate
יתרונות הגישה הדינמית:
  • ✓ Zero Deployment Downtime: הוספת מחלקות מסמכים תוך שניות בודדות.
  • ✓ EventBridge Invalidation: פונקציות ה-Lambda מקבלות אירוע עדכון ומרעננות את ה-Ajv Cache המקומי שלהן.
  • ✓ Backward Compatibility Check: בדיקה אוטומטית שהסכמה החדשה אינה שוברת מסמכים קיימים.
